Developer Integration Guide

Generate student ID cards from your app with a handful of clean calls. This guide covers the Python SDK, the REST web API, and the web server for template previews.

Python · FastAPI · Open Source

Quick Start

Install the dependencies and start the preview server in two commands.

Terminal
pip install -r requirements.txt
# start the web UI (optional, for template previews)
python -m card_sdk.web_server
Note
The package lives in sdk/card_sdk/. Add the sdk/ folder to your PYTHONPATH or install it so import card_sdk resolves to the repo copy.

Generating a Card

For a single card, generate_card() is all you need. It returns a status string and writes the finished PDF to the output folder.

example.py
from card_sdk.card import generate_card, image_file_to_base64

result = generate_card(
    template_name="BLUE GREEN STUDENT CARD",
    image_base64=image_file_to_base64("student.jpg"),
    student_name="Tuyishimire Fraterine Ely",
    student_class="Software Development",
    school_name="KANYINYA TSS 001",
    student_id="S-2026-001",
    data_qrcode="https://kaascan.com/verify/S-2026-001",
)
print(result)  # status message + output path

Output goes to output/<school_name>/<class>/final_student_card_<id>.pdf.

Config Object

Wrap your data in a CardConfig. It centralises the values and can build a pydantic Student model for the asynchronous batch flow.

config_usage.py
from card_sdk.card import CardConfig, image_file_to_base64

photo = image_file_to_base64("student.jpg")

cfg = CardConfig(
    photo=photo,                                      # required: base64 student photo
    template_name="BLUE GREEN STUDENT CARD",
    student_name="Tuyishimire Fraterine Ely",
    student_class="Software Development",
    school_name="KANYINYA TSS 001",
    student_id="S-2026-001",
    data_qrcode="https://kaascan.com/verify/S-2026-001",
    # optional branding: school_logo, stamp, signature, barcode (all base64)
)

# Option A: render the card content dict
content = cfg.generate_card_content()    # renders card + writes PDF

# Option B: build a Student model for the async batch API
student = cfg.to_student()              # card_sdk.card_agent.Student instance

Branding Assets

Pass base64-encoded assets as optional keyword arguments. Every parameter has a sensible default, so integrations only need to send what they have.

branding.py
from card_sdk.card import generate_card, image_file_to_base64

result = generate_card(
    template_name="BLUE GREEN STUDENT CARD",
    image_base64=image_file_to_base64("student.jpg"),
    student_name="Alice Johnson",
    student_class="Grade 4",
    school_name="SUNRISE ACADEMY",
    student_id="A-001",
    data_qrcode="https://kaascan.com/verify/A-001",
    # ---- optional branding ----
    school_logo=image_file_to_base64("logo.png"),
    stamp_base64=image_file_to_base64("stamp.png"),
    student_barcode=image_file_to_base64("barcode.png"),
    signature_base64=image_file_to_base64("signature.png"),
    side_2_color="#00897B",
)

Web Server

Start the FastAPI web UI from the terminal. This is what the terminal UI's “Start the web server to view templates?” prompt calls for you.

Terminal
python -m card_sdk.web_server                  # port 8000
python -m card_sdk.web_server --port 9000
python -m card_sdk.web_server --host 127.0.0.1

Or start it from code:

Python
from card_sdk.web_server import serve_web
serve_web(host="0.0.0.0", port=8000)   # blocks until interrupted

The server binds to the local dev SDK automatically (it adds the repo to the path), so you always see the real templates.

Authentication

The admin API key is never embedded in code. Every run of the terminal agent (await Card.agent(...)) starts a QR-code handshake: a scannable code — plus the plain endpoint URL — is printed in the terminal, and your web service (WS) posts the key back to authorize the SDK. Once authorized, card generation (SINGLE / MULTIPLE) is unlocked.

No hard-coded keys

The SDK ships without an API key. The key arrives at runtime through the handshake or an environment variable.

Live validation

The submitted key is verified against the Kaascan admin API before the SDK is authorized.

In-memory only

The key stays in process memory for the X-API-KEY header and is never written to disk.

How the handshake works

On startup the SDK starts a tiny local HTTP endpoint on port 8132, prints the QR code (encoding http://<lan-ip>:<port>/auth?token=…) and waits. Scan the code with a phone (a small authorize page opens), or point your web service at the endpoint and post the key:

Terminal · SDK
[AUTH] Authorize the API user
Scan the QR code (or open the endpoint) and post the
'admin_api_key' your web service will send back.

  Endpoint -> http://192.168.1.50:8132/auth?token=1f3c9a...
  (scannable QR code printed here)

  Waiting 180s for authorization ... (Ctrl+C to abort)

  [+] admin_api_key accepted — SDK authorized.
  [✓] API user authorized — card generation unlocked.
curl · Web service (WS)
curl -X POST "http://192.168.1.50:8132/auth?token=1f3c9a..." \
  -H "Content-Type: application/json" \
  -d '{ "admin_api_key": "YOUR_ADMIN_API_KEY" }'

# → {"ok": true, "authorized": true, "message": "authorized"}
Skip the handshake for automation
Set KAA_SCAN_API_KEY=<key> in the environment and the handshake is skipped — the SDK uses it directly. The runtime QR flow is only shown when no key is pre-configured.

Auth endpoints

MethodEndpointPurpose
GET/Tiny HTML authorize page — open it with a phone to paste the key.
POST/authReceive + validate admin_api_key (JSON or form). Adds ?token=… from the QR.
GET/auth/statusJSON status of the current session (authorized, error).

Validation behaviour

How a submitted key is checked
The key is probed against https://api.v2.kaascan.com/admin/students: a valid students payload → authorized; an HTTP error (401/403) → rejected; the API unreachable (offline machine) → accepted with a printed warning that it could not be verified remotely.

Configuration

VariableDefaultPurpose
KAA_SCAN_API_KEY(unset)Env-supplied admin key — skips the QR handshake.
KAA_AUTH_HOST0.0.0.0Bind host for the auth endpoint.
KAA_AUTH_PORT8132Bind port (a free port is chosen if busy).
KAA_AUTH_TIMEOUT180Seconds to wait for the WS before giving up.

Template Versioning

Card designs live as SVG source files in card_sdk/templates/templates_base/<template>/. The generator reads a minified .card.kaascan file for each side, so applying a design update used to mean hand-collapsing the SVG and re-editing every card. The versioning CLI turns template design into simple, git-style commands.

When a designer ships a new look, drop front.svg / back.svg into the template folder and commit. The design is snapshotted, the .card.kaascan files are rebuilt so the generator picks it up immediately, and it becomes the active version. Old designs stay under versions/ and can be restored at any time — no card rewriting needed.

Terminal
python3 -m card_sdk.template_versioning build BANK_INSPIRE
python3 -m card_sdk.template_versioning commit BANK_INSPIRE --label spring-2026 --message "Spring rebrand"
python3 -m card_sdk.template_versioning list
python3 -m card_sdk.template_versioning current BANK_INSPIRE
python3 -m card_sdk.template_versioning rollback BANK_INSPIRE --label v1

Folder layout

Tree
templates_base/BANK_INSPIRE/
├── front.svg  ·  back.svg                       # working design (source of truth)
├── front.card.kaascan  ·  back.card.kaascan     # rebuilt from the svg — generator reads these
└── versions/
    ├── .current                                 # active label
    ├── v1/          (front.svg, back.svg, meta.json)   # one snapshot per label, like a branch
    └── spring-2026/ (front.svg, back.svg, meta.json)

Commands

CommandPurpose
build <template>Rebuild the .card.kaascan files from the SVGs in the folder — e.g. right after hand-editing a design. Warns about missing standard placeholders.
commit <template> --label <name> [--message "…"]Snapshot the current design under versions/<label>, sync the .kaascan cards and mark it active. Reusing a label needs --force.
list [<template>]All committed versions (label, date, message); * marks the active one. Without a template it covers every installed template.
current <template>Show the active version label.
rollback <template> --label <name>Restore the working SVG + .kaascan from a saved snapshot and make that design active again.
Workflow
Designer drops front.svg + back.svg → commit --label spring-2026 → cards render with the new design immediately; the previous design is still one rollback --label v1 away.
Keep the placeholders
Card data is filled through {…} placeholders inside the SVG ({name}, {student_code}, {student_class}, {school_name}, {student_id}, {student_photo}, {student_barcode}, {valid_thru}, {school_type}). build / commit warn when a freshly-dropped design is missing one, so card fields never silently stay empty.
